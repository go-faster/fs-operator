# Acknowledged CRD changes: findings hack/check-crd-compat.py reports that a
# human has decided are safe.
#
# The checker is deliberately conservative — it compares schemas, and cannot
# see the objects a cluster actually holds. A tightened rule that every stored
# object already satisfies is safe, and this is where that gets written down.
#
# One finding per line, copied verbatim from the checker's output, and each
# preceded by a comment saying why it is safe. A line with no justification is
# a line nobody reviewed.

# Single-node mode made spec.etcd optional altogether, so the "exactly one of
# them" rule became "at most one": a single-node cluster declares neither, and
# which case applies is a cross-field question CEL cannot answer from inside
# spec.etcd (internal/validation does). The new rule is strictly weaker than
# the one it replaces — anything that satisfied "exactly one" satisfies "at
# most one" — so every stored object still validates. It supersedes the rule
# acknowledged here before it, which the CRD no longer carries:
# 'has(self.external) != has(self.managed)'.
FSCluster/v1alpha1.spec.etcd: new validation rule '!has(self.external) || !has(self.managed)'

# The shared OTLP transport lost its default so that leaving it unset means
# something: unset is what lets a per-signal OTEL_EXPORTER_OTLP_<SIGNAL>_PROTOCOL
# take effect, since fs's SDK reads the shared variable first. Nothing changes
# for a stored object — the API server already materialised 'grpc' into it, and
# grpc is also what the SDK falls back to — so every existing cluster renders
# the transport it rendered before.
FSCluster/v1alpha1.spec.observability.otlp.protocol: default 'grpc' -> None

# fs v0.14 (operator v0.9.0) is a deliberate break of v1alpha1, decided over a
# new API version: fs v0.14 cannot read a v0.13 cluster's data (the engine
# replaced the filesystem backend, the layout replaced etcd), so no stored
# FSCluster survives the upgrade — every one is deleted and recreated, and its
# FSBuckets and FSAccessKeys with it. A conversion to a new version would
# preserve objects that describe clusters nothing can run. The upgrade notes
# say to delete them before installing the new CRDs. These findings are that
# break, and nothing else.
FSBucket/v1alpha1.spec.scheme: pattern '^(rf2\\.5|rf3|ec:[0-9]+,[0-9]+)?$' -> '^(rf3|ec:[1-9][0-9]*,[1-9][0-9]*)?$'
FSCluster/v1alpha1.spec.etcd: removed (stored objects lose this field)
FSCluster/v1alpha1.spec.integrity: removed (stored objects lose this field)
FSCluster/v1alpha1.spec.rebalance: removed (stored objects lose this field)
FSCluster/v1alpha1.spec.scheme: removed (stored objects lose this field)
FSCluster/v1alpha1.spec.storage.disks: removed (stored objects lose this field)
FSCluster/v1alpha1.spec.storage.state: removed (stored objects lose this field)
FSCluster/v1alpha1.spec.storage.size: newly required
FSCluster/v1alpha1.spec.topology.nodes: new validation rule 'self != 2'
FSCluster/v1alpha1.spec.updatePolicy.schemaMigration: removed (stored objects lose this field)
FSCluster/v1alpha1.status.rebalance: removed (stored objects lose this field)
FSCluster/v1alpha1.status.registeredNodes: removed (stored objects lose this field)
FSCluster/v1alpha1.status.schemaVersion: removed (stored objects lose this field)
FSCluster/v1alpha1.status.update.disk: removed (stored objects lose this field)
FSCluster/v1alpha1.status.update.phase: enum value 'Migrating' no longer accepted
